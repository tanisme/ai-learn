# 二、先理解三种完全不同的操作

我们先看三种操作：

```
import copya = [1, 2, 3]# 方式一：普通赋值b = a# 方式二：浅拷贝c = copy.copy(a)# 方式三：深拷贝d = copy.deepcopy(a)
```

这三种操作看起来都得到了一个新的变量，但它们的对象关系并不一样。

## 2.1 普通赋值：只建立新的引用

```
a = [1, 2, 3]b = aprint(a is b)
```

输出：

```
True
```

这里没有创建新的列表对象。

`a` 和 `b` 指向同一个列表。

普通赋值

变量 a

变量 b

同一个列表对象\
`[1, 2, 3]`

因此：

```
b.append(4)print(a)
```

输出：

```
[1, 2, 3, 4]
```

## 2.2 浅拷贝：只复制最外层容器

现在看：

```
import copya = [1, 2, 3]b = copy.copy(a)print(a is b)print(a == b)
```

输出：

```
False
True
```

这次确实创建了一个新的列表对象。

但要注意：

浅拷贝只复制最外层容器，容器内部的元素仍然可能引用原来的对象。

例如：

```
import copya = [    [1, 2],    [3, 4]]b = copy.copy(a)print(a is b)print(a[0] is b[0])print(a[1] is b[1])
```

输出：

```
False
True
True
```

这说明：

- 外层列表是新的对象。
- 内层列表仍然是原来的对象。

浅拷贝对象关系

原列表 a

`[1, 2]`

`[3, 4]`

新列表 b

共享对象

`[1, 2]`

共享对象

`[3, 4]`

两个外层列表独立，但内部元素共享引用。

因此，修改内层列表会产生影响：

```
import copya = [[1, 2], [3, 4]]b = copy.copy(a)b[0].append(100)print(a)print(b)
```

输出：

```
[[1, 2, 100], [3, 4]]
[[1, 2, 100], [3, 4]]
```

为什么？

因为：

```
a[0] is b[0]
```

结果为 `True`。

## 2.3 深拷贝：递归复制内部对象

现在看：

```
import copya = [    [1, 2],    [3, 4]]b = copy.deepcopy(a)print(a is b)print(a[0] is b[0])print(a[1] is b[1])
```

输出：

```
False
False
False
```

深拷贝会递归复制内部对象，使新对象与原对象在通常情况下形成独立的对象结构。

例如：

```
import copya = [[1, 2], [3, 4]]b = copy.deepcopy(a)b[0].append(100)print(a)print(b)
```

输出：

```
[[1, 2], [3, 4]]
[[1, 2, 100], [3, 4]]
```

深拷贝对象关系

原对象 a

`[1, 2]`

`[3, 4]`

新对象 b

`[1, 2]`

`[3, 4]`

外层容器和内部可复制对象都分别创建。

# 三、Python copy 模块深入

Python 标准库提供了 `copy` 模块。

主要包含两个接口：

```
import copycopy.copy(obj)copy.deepcopy(obj)
```

下面深入分析它们的行为。

## 3.1 copy.copy() 的常见用法

列表：

```
import copydata = [1, 2, 3]new_data = copy.copy(data)
```

字典：

```
data = {    "name": "Agent",    "skills": ["Python", "RAG"]}new_data = copy.copy(data)
```

集合：

```
data = {1, 2, 3}new_data = copy.copy(data)
```

也可以使用一些容器自身的复制方法：

```
new_list = old_list.copy()new_dict = old_dict.copy()new_set = old_set.copy()
```

对于这些常见内置容器，上述方法通常提供浅拷贝语义。

## 3.2 copy.deepcopy() 的常见用法

```
import copydata = {    "agent": {        "name": "ResearchAgent",        "config": {            "temperature": 0.2,            "tools": ["search", "browser"]        }    }}new_data = copy.deepcopy(data)new_data["agent"]["config"]["tools"].append(    "calculator")print(data)print(new_data)
```

原对象不会受到新对象中嵌套列表修改的影响。

注意，深拷贝不等于将整个 Python 运行环境复制一遍。文件句柄、Socket、线程、锁、数据库连接等资源不能简单地通过深拷贝得到一个独立且有效的副本。

## 四、深拷贝的底层机制：memo 字典

这一部分是本节最重要的深入知识点，也是中高级 Python 面试经常考察的内容。

很多人知道 `deepcopy()` 可以递归复制对象，但不知道它是如何处理循环引用和共享对象的。

CPython 的 `copy` 模块通过一个非常重要的数据结构解决这个问题：

memo：对象复制过程中使用的临时备忘录。

## 4.1 为什么需要 memo？

先看一个普通的嵌套对象：

```
data = [    [1, 2],    [3, 4]]
```

深拷贝时，可以依次复制：

1. 创建新的外层列表。
2. 复制第一个内部列表。
3. 复制第二个内部列表。

但如果对象存在循环引用，就会出现问题。

例如：

```
data = []data.append(data)print(data)
```

这里列表引用了自己。

对象关系是：

循环引用对象

列表对象 A

第一个元素引用自身

仍然指向 A

如果深拷贝不做处理：

```
复制 A
  └── 复制 A
       └── 复制 A
            └── 无限递归
```

因此，需要记录已经复制过的对象。

## 4.2 memo 的工作原理

假设原对象是 A，深拷贝过程如下：

1. 检查 memo 中是否已经存在 A。
2. 如果存在，直接返回 A 对应的新对象。
3. 如果不存在，创建新对象 A'。
4. 将 `memo[id(A)] = A'`。
5. 递归复制 A 的内部元素。
6. 如果内部元素又引用 A，就直接从 memo 中取得 A'。

这样就能避免无限递归。

Deepcopy + memo 执行流程

原对象 A

检查 memo：是否已复制？

已复制

返回 memo 中的 A'

未复制

创建 A' 并记录 memo

递归复制内部对象

## 4.3 验证循环引用的深拷贝

```
import copydata = []data.append(data)new_data = copy.deepcopy(data)print(data is new_data)print(new_data is new_data[0])print(data is data[0])
```

输出：

```
False
True
True
```

解释：

- `data is new_data`：两个外层列表不是同一个对象。
- `new_data is new_data[0]`：新列表的第一个元素引用新列表自身。
- `data is data[0]`：原列表的第一个元素引用原列表自身。

这说明深拷贝不仅复制了对象，还保留了原对象内部的循环引用结构。

## 4.4 验证共享引用

再看一个更容易被忽视的情况：

```
import copyshared = [1, 2, 3]data = {    "first": shared,    "second": shared}new_data = copy.deepcopy(data)print(data["first"] is data["second"])print(new_data["first"] is new_data["second"])print(data["first"] is new_data["first"])
```

输出：

```
True
True
False
```

这说明：

- 原对象中 `first` 和 `second` 共享同一个列表。
- 深拷贝后，新对象中 `first` 和 `second` 仍然共享同一个新列表。
- 但是新列表与原列表相互独立。

这是非常重要的细节：

深拷贝并不是把每一个引用都复制成独立对象，而是尽可能保留对象图中的共享关系，同时创建对应的副本。

# 五、自定义对象的复制机制

在企业级 Agent 系统中，我们通常不会只操作 list 和 dict。

还会定义大量自定义对象：

- AgentConfig
- AgentContext
- ToolContext
- TaskContext
- ExecutionState
- ConversationSession

这就涉及自定义对象的复制行为。

## 5.1 默认情况下如何复制自定义对象？

例如：

```
import copyclass AgentConfig:    def __init__(self, name, tools):        self.name = name        self.tools = toolsconfig = AgentConfig(    "ResearchAgent",    ["search", "browser"])new_config = copy.copy(config)print(config is new_config)print(config.tools is new_config.tools)
```

输出：

```
False
True
```

默认情况下，对于这种普通自定义类实例：

- 外层实例被复制。
- 实例属性中引用的对象通常仍然共享。

## 5.2 自定义 `__copy__()` 方法

如果我们希望控制浅拷贝行为，可以定义：

```
def __copy__(self):    ...
```

完整示例：

```
import copyclass AgentConfig:    def __init__(self, name, tools):        self.name = name        self.tools = tools    def __copy__(self):        # 创建新的配置对象        new_obj = type(self).__new__(type(self))        # 复制不可变字段        new_obj.name = self.name        # tools 这里仍然共享引用        new_obj.tools = self.tools        return new_objconfig = AgentConfig(    "ResearchAgent",    ["search", "browser"])new_config = copy.copy(config)print(config is new_config)print(config.tools is new_config.tools)
```

输出：

```
False
True
```

这里手动实现了浅拷贝。

注意：自定义类如果存在继承关系、`__slots__`、描述符或特殊资源属性，就需要根据自身结构设计复制逻辑，不能机械地复制这个示例。

## 5.3 自定义 `__deepcopy__()` 方法

深拷贝的自定义接口：

```
def __deepcopy__(self, memo):    ...
```

这里有一个重要参数：

```
memo
```

它就是前面讲到的对象复制备忘录。

完整代码：

```
import copyclass AgentConfig:    def __init__(self, name, tools, settings):        self.name = name        self.tools = tools        self.settings = settings    def __deepcopy__(self, memo):        # 检查当前对象是否已经被复制        object_id = id(self)        if object_id in memo:            return memo[object_id]        # 创建未初始化的新对象        new_obj = type(self).__new__(type(self))        # 先登记对象，避免循环引用        memo[object_id] = new_obj        # 深拷贝各个属性        new_obj.name = copy.deepcopy(            self.name,            memo        )        new_obj.tools = copy.deepcopy(            self.tools,            memo        )        new_obj.settings = copy.deepcopy(            self.settings,            memo        )        return new_objif __name__ == "__main__":    config = AgentConfig(        name="ResearchAgent",        tools=["search", "browser"],        settings={            "temperature": 0.2,            "max_tokens": 4096        }    )    new_config = copy.deepcopy(config)    new_config.tools.append("calculator")    new_config.settings["temperature"] = 0.8    print("原始配置:", config.tools)
```

输出：

```
原始配置: ['search', 'browser']
新配置: ['search', 'browser', 'calculator']

原始温度: 0.2
新温度: 0.8
```

这就是自定义深拷贝的基本实现。

需要记住两个关键步骤：

```
memo[object_id] = new_obj
```

以及：

```
copy.deepcopy(attribute, memo)
```

前者用于登记当前对象，后者保证嵌套对象也使用同一个 memo。

## 5.4 哪些对象不应该随便深拷贝？

下面这些对象尤其需要注意：

| 对象            | 处理建议       |
| ------------- | ---------- |
| 普通配置字典        | 可以深拷贝      |
| 嵌套列表          | 根据是否需要隔离决定 |
| 文件句柄          | 不应直接深拷贝    |
| Socket        | 不应直接深拷贝    |
| 数据库连接         | 应通过连接池管理   |
| Thread / Task | 不应复制执行实体   |
| Lock          | 不应随意复制     |
| 大型模型对象        | 通常共享或单独管理  |
| HTTP Client   | 通过生命周期管理复用 |

例如，下面的做法就不合理：

```
import copyimport threadinglock = threading.Lock()# 不应该假设锁可以被安全深拷贝new_lock = copy.deepcopy(lock)
```

正确思路是根据业务创建独立的锁，或者通过依赖注入共享同一个受控锁。

# 六、浅拷贝与深拷贝的性能分析

这是工程师与只会使用 Python 的开发者之间的重要区别。

很多人认为：

> 深拷贝更安全，所以所有对象都应该使用 deepcopy。

这个理解是错误的。

深拷贝需要遍历对象结构，并可能创建大量新对象。

因此，可能造成：

- CPU 开销增加。
- 内存占用增加。
- GC 工作量增加。
- Agent 执行延迟增加。

## 6.1 性能测试

下面通过实际程序对比三种操作。

```
import copyimport timeimport tracemallocdef create_data():    return {        "agent": "ResearchAgent",        "messages": [            {                "role": "user",                "content": f"Message {i}",                "metadata": {                    "timestamp": i,                    "tags": ["agent", "python", "rag"]                }            }            for i in range(10000)        ]    }def benchmark(name, func, data, repeat=100):    start = time.perf_counter()    for _ in range(repeat):        result = func(data)    elapsed = time.perf_counter() - start    print(        f"{name:<20} "        f"{elapsed:.6f} seconds"    )    return resultif __name__ == "__main__":    data = create_data()    tracemalloc.start()    benchmark(        "普通赋值",        lambda x: x,        data    )    benchmark(        "浅拷贝",        copy.copy,        data    )    benchmark(        "深拷贝",        copy.deepcopy,        data
```

这段程序会测试：

1. 普通赋值。
2. 浅拷贝。
3. 深拷贝。

实际运行时间取决于机器性能、Python 版本、对象结构和系统负载，不应预设固定比例。

## 6.2 三种操作的复杂度理解

| 操作   | 典型时间成本      | 新对象数量    |
| ---- | ----------- | -------- |
| 普通赋值 | 通常 O(1)     | 不创建容器副本  |
| 浅拷贝  | O(n)        | 创建外层容器   |
| 深拷贝  | 与可遍历对象图规模相关 | 可能创建大量对象 |

这里的 n 指被复制的容器元素数量；深拷贝还需要考虑嵌套对象和共享引用。

## 6.3 如何选择？

我的建议：

- 只是想让另一个变量引用同一个对象：普通赋值。
- 只想隔离最外层容器：浅拷贝。
- 需要隔离嵌套数据结构：深拷贝。
- 对象很大且存在复杂资源：设计专门的复制策略。
- 多个 Agent 共享只读数据：优先考虑共享，不必复制。

# 七、浅拷贝与深拷贝在 AI Agent 中的应用

这一部分是本节最重要的工程实践。

前面学习的是 Python 本身的复制机制，现在将这些知识放进真实 Agent 架构中。

## 7.1 场景一：Research Agent 与 Summary Agent 共享状态

假设我们有一个多 Agent 系统：

- Research Agent：负责收集研究结果。
- Summary Agent：负责生成摘要。
- Report Agent：负责生成最终报告。

初始状态：

```
state = {    "task_id": "task-001",    "research": {        "keywords": ["Agent", "RAG"],        "results": [            {                "title": "Agent Architecture",                "content": "Agent system design..."            }        ]    },    "summary": {},    "report": {}}
```

现在，Research Agent 将状态传递给 Summary Agent。

错误写法：

```
import copydef research_agent(state):    return statedef summary_agent(state):    new_state = copy.copy(state)    new_state["research"]["results"].clear()    new_state["summary"] = {        "content": "Research completed"    }    return new_statestate = {    "research": {        "results": ["Result A", "Result B"]    },    "summary": {}}research_agent(state)new_state = summary_agent(state)print("原状态:", state)print("新状态:", new_state)
```

这里使用了浅拷贝。

但：

```
new_state["research"] is state["research"]
```

结果为 `True`。

因此：

```
new_state["research"]["results"].clear()
```

实际上修改了原始状态。

这就产生了数据污染。

## 7.2 方案一：使用 deepcopy 隔离状态

```
import copydef summary_agent(state):    new_state = copy.deepcopy(state)    new_state["research"]["results"].clear()    new_state["summary"] = {        "content": "Research completed"    }    return new_state
```

这种方式能够隔离嵌套数据。

但如果 State 包含几十万条消息、大型工具结果或者其他复杂对象，深拷贝可能带来明显的性能成本。

因此，更推荐在很多 Agent 工作流中采用第二种方案。

## 7.3 方案二：只返回需要更新的字段

```
from typing import Any, Dictdef summary_agent(    state: Dict[str, Any]) -> Dict[str, Any]:    research_results = state["research"]["results"]    summary = {        "content": (            f"研究完成，共收集 "            f"{len(research_results)} 条结果"        )    }    return {        "summary": summary    }
```

这种方式有几个优点：

1. 不复制整个 State。
2. 不修改输入 State。
3. 只返回需要更新的字段。
4. 更容易进行单元测试。
5. 更容易实现节点之间的状态隔离。

这也是 LangGraph 节点开发中非常重要的编程习惯。

需要注意：返回更新并不意味着所有嵌套对象天然不可变。如果节点拿到共享的可变对象后直接修改它，仍然可能造成副作用。

## 7.4 方案三：使用不可变数据结构

对于某些关键业务状态，可以考虑使用不可变数据结构。

例如使用 Python 的 `dataclass`：

```
from dataclasses import dataclass, replacefrom typing import Tuple@dataclass(frozen=True)class ResearchResult:    title: str    content: str@dataclass(frozen=True)class AgentState:    task_id: str    results: Tuple[ResearchResult, ...]    summary: strstate = AgentState(    task_id="task-001",    results=(        ResearchResult(            title="Agent Architecture",            content="Agent design..."        ),    ),    summary="")new_state = replace(    state,    summary="Research completed")print(state.summary)print(new_state.summary)
```

输出：

```

Research completed
```

这里：

- `state` 没有被修改。
- `new_state` 是一个新状态对象。
- 两者可以安全地共享不可变的 `results` 元组及其不可变元素。

注意，`frozen=True` 是浅层冻结。如果属性中包含普通列表或字典，仍然可以修改其内部内容。因此，要实现真正的不可变状态，需要配合不可变的嵌套数据结构。

# 八、Pydantic 中的深浅拷贝

在 AI Agent 后端项目中，Pydantic 使用非常广泛。

例如：

- Agent 配置对象。
- Tool 参数对象。
- API 请求对象。
- 执行上下文。
- 任务状态对象。

因此，需要了解 Pydantic 自身的复制接口。

以下示例以 Pydantic 2.x 为准。

## 8.1 model_copy() 的基本用法

```
from pydantic import BaseModelfrom typing import Listclass AgentConfig(BaseModel):    name: str    tools: List[str]    temperature: floatconfig = AgentConfig(    name="ResearchAgent",    tools=["search", "browser"],    temperature=0.2)
```

浅拷贝：

```
new_config = config.model_copy()print(config is new_config)print(config.tools is new_config.tools)
```

输出：

```
False

```

## 8.3 model_copy(update=...) 的注意事项

例如：

```
new_config = config.model_copy(    update={        "temperature": 0.8    })
```

可以在复制时更新指定字段。

但需要注意：

`model_copy(update=...)` 不会对 update 中提供的数据自动执行完整的 Pydantic 校验。

如果更新值来自不可信的外部输入，不能把它当成经过校验的 API 数据。

必要时应该重新通过模型验证入口构建对象。

这属于非常实用的面试知识点。

# 九、Agent 状态复制的最佳实践

将目前学到的知识整理成工程规范。

| 使用场景          | 推荐方案        | 原因       |
| ------------- | ----------- | -------- |
| 普通变量传递        | 直接赋值        | 无额外复制成本  |
| 小型字典更新        | 浅拷贝         | 隔离外层结构   |
| 复杂嵌套状态        | 按需深拷贝       | 避免嵌套数据污染 |
| 只读共享配置        | 共享不可变对象     | 减少内存占用   |
| Agent 节点输出    | 返回字段更新      | 明确状态边界   |
| Pydantic 配置复制 | model_copy  | 使用模型原生机制 |
| 大型消息历史        | 增量更新、持久化    | 避免重复复制   |
| 并发任务状态        | 独立任务状态或明确同步 | 防止竞争条件   |

## 9.1 特别注意并发问题

假设两个异步 Agent 同时操作同一个列表：

```
import asyncioshared_results = []async def agent_a():    for i in range(1000):        shared_results.append(f"A-{i}")        await asyncio.sleep(0)async def agent_b():    for i in range(1000):        shared_results.append(f"B-{i}")        await asyncio.sleep(0)async def main():    await asyncio.gather(        agent_a(),        agent_b()    )    print(len(shared_results))asyncio.run(main())
```

这个示例在当前运行条件下通常会得到 2000 条记录，但它不代表共享状态就一定安全。

如果后续操作包含：

- 读取后判断再修改。
- 多步骤状态更新。
- 读写多个关联字典。
- 跨线程共享对象。

就可能出现竞态条件。

例如：

```
if "task-001" not in shared_results:    shared_results.append("task-001")
```

这两个操作不是一个原子业务事务。

可能出现多个任务同时判断不存在，然后都执行添加。

常见解决方法：

1. `asyncio.Lock`：保护同一事件循环中的协程共享状态。
2. `threading.Lock`：保护多线程共享状态。
3. 独立任务状态：避免多个 Agent 修改同一个对象。
4. 消息队列：通过消息传递实现模块解耦。
5. 数据库事务与唯一约束：保证持久化数据的一致性。

不要把深拷贝当成并发安全的替代方案。 它只能解决部分对象共享问题，不能解决所有同步与事务问题。

## 10.3 core/state_manager.py

负责状态复制与更新。

```
        """        浅拷贝状态        """        return state.model_copy()    @staticmethod    def deep_copy(        state: AgentState    ) -> AgentState:        """        深拷贝状态        """        return state.model_copy(deep=True)    @staticmethod    def update(        state: AgentState,        updates: Dict[str, Any]    ) -> AgentState:        """        创建更新后的状态        使用深拷贝隔离原状态，        再对副本执行更新。        """        new_state = state.model_copy(deep=True)        for key, value in updates.items():            if not hasattr(new_state, key):                raise ValueError(                    f"未知状态字段: {key}"                )            setattr(new_state, key, value)        new_state.version += 1        return new_state
```

这里有一个工程上的注意事项：

`setattr()` 赋值并不会自动保证任意输入值都通过 Pydantic 完整验证。如果 updates 来自外部不可信数据，后续还需要增加专门的字段验证逻辑。

| 面试问题               | 核心回答                          |
| ------------------ | ----------------------------- |
| 什么是浅拷贝？            | 复制最外层对象，内部引用可能共享              |

| 如何避免 Agent 状态污染？   | 明确状态更新边界，必要时复制嵌套数据            |

## 12.2 中高级场景题

问题一：为什么在 Agent 系统中不能随意使用 deepcopy？

参考答案：

Agent State 可能包含大量对话历史、工具结果和嵌套数据结构。深拷贝会增加 CPU 和内存开销。

应该根据状态的所有权和使用方式，采用增量更新、不可变对象、浅拷贝或必要的深拷贝。

问题二：LangGraph 的节点为什么推荐返回状态更新，而不是直接修改 State？

参考答案：

返回状态更新能够明确节点的输出边界，降低共享可变对象造成的副作用，并使 Graph 可以按照 State Schema 和 Reducer 规则合并更新。

问题三：深拷贝如何处理两个字段引用同一个对象的情况？

参考答案：

使用 memo 保存原对象 ID 和对应副本之间的映射，保证共享引用关系在复制后得到保留。

问题四：如果一个对象包含数据库连接，应该如何深拷贝？

参考答案：

不应该直接复制数据库连接。应该共享连接池管理器，或者通过依赖注入为不同执行任务提供合适的连接。

# 十五、1.2 本节总结与下一节安排

本节需要真正掌握的不是简单记住 `copy.copy()` 和 `copy.deepcopy()`，而是建立以下工程认知：

1. 赋值、浅拷贝、深拷贝是三种不同的操作。
2. 浅拷贝只隔离外层容器。
3. 深拷贝通过递归复制和 memo 机制处理复杂对象关系。
4. 自定义对象可以通过 `__copy__` 和 `__deepcopy__` 控制复制行为。
5. Pydantic 提供 `model_copy(deep=True)`。
6. Agent 系统应该根据状态所有权选择复制策略，而不是盲目深拷贝。
7. 对于并发状态，复制不能代替锁、事务和正确的状态管理。
